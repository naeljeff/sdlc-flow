# Team evaluation protocol

The approved experiment contains eight matched pilot attempts, then a
conditional forty-workflow bank. This document describes execution gates; it
does not claim either study has completed or established a performance ranking.
Runnable commands and manifest contracts are in
[tests/team/README.md](../../tests/team/README.md).

## Study separation

1. Mechanical checks validate state/ownership rules and reject semantic
   integration failures. These are not model outcomes.
2. Native compatibility probes validate fresh sessions, actual host tools,
   heterogeneous worker selection and overlapping execution separately per host.
3. One dependent product trajectory covers ten controlled fresh-session resets
   (eleven sessions), including changed requirements, stale verification,
   interrupted work, live ownership and unrelated dirty files. These are fresh
   sessions, not an unobserved native compaction event.
4. A real-repository pilot compares candidate versus `dev`, two new tasks, two
   repetitions each: eight full workflows with the same source, effective
   requirements, native backend, routing, tool allowance and concurrency.
5. Only a valid passing pilot and release-critical prerequisites can authorize
   the planned forty workflows: four new task families × five workflows × two
   repetitions. A failed prerequisite is a recorded blocker, not an invitation
   to manufacture a favorable ranking.

## Frozen assessment

Use complete maintained repository snapshots with exact source provenance and
licenses intact. Keep task-author reference implementations and grader outcomes
outside all candidate paths. Fresh subjects must not receive private controls,
old v8 graders, prior attempts, or reference PR patches. Git history stays at the
actual pinned upstream revision, and an identical unrelated dirty overlay is
added to every subject.

Before any scored session, independently validate unchanged baselines, positive
behavior controls, per-requirement negative controls, and combined-feature
counterexamples. Import errors and infrastructure crashes cannot stand in for
expected product failures. Positive reference controls certify only the outcome
surface they actually check. Useful tests, user-facing docs and independent
integrated review are separate mandatory acceptance IDs with a fresh review
receipt tied to each frozen candidate.

The initial private pack uses TinyDB at
`18d73a15066a04c77f19ae9a8c03d582bd344c0d`
([upstream](https://github.com/msiemens/tinydb)) and python-dotenv at
`0b2880591780a426b0551436f47a17e7a76d954f`
([upstream](https://github.com/theskumar/python-dotenv)). They exercise optional
storage isolation plus atomic batch input handling, and explicit environment
evaluation plus alternate interpolation, respectively. Their exact briefs,
controls and outcome scripts remain private. They are proposed feature tasks
authored for this study on real projects, not upstream accepted feature patches.

An independent initial audit found missing exception-identity and keyword-only
checks and a tests/docs acceptance gap. The assessment was revised before any
scored session: exception propagation and signatures gained counterexamples,
and qualitative requirements gained a mandatory per-run independent gate.
Passing self-authored controls alone was not treated as sufficient evidence.

## Matched host adaptations

Both arms receive an identical approved instruction: the effective brief
authorizes implementation; do not commit or publish; native spawn/message/wait
may implement the unavailable `Workflow` control flow. Both receive the same
frozen dependency index and source copies. Record this adapted baseline in the
report; do not describe it as an unmodified installation.

The installed `dev` names `superpowers:*` dependencies. The local equivalents
are explicit `sp-*` aliases, copied and hashed privately. The missing exact
`security-review` alias maps to the installed `ecc-security-review` variant by
explicit approval, with that difference recorded. The missing
`karpathy-guidelines` is taken from the
[primary repository](https://github.com/multica-ai/andrej-karpathy-skills), pinned
at `2c606141936f1eeef17fa3043a72095b4765b9c2`, path
`skills/karpathy-guidelines/SKILL.md`. No global installation or configuration
change is required. Conditional UI dependencies are not invoked for these
Python-library tasks.

An alias or authenticated account does not prove a requested provider model is
available. Record requested model separately from host-reported route identity.
Worker identities must come from structured host/session records. If native
selection is unsupported, a heterogeneous requirement fails explicitly.
External subprocess-provider workers form a different experiment. Different
backends are never silently treated as a matched candidate/`dev` comparison.

## Accounting and claims

Retain every orchestrator, worker, reviewer, retry and rework receipt privately.
Measure root process duration and time from the first attempt to independently
accepted outcome, but label missing detached-worker/reviewer coverage. Keep
input, output, cache observations and monetary cost separate; do not turn
missing usage into zero or infer prices. No token ceiling decides success.

Report required outcomes, regressions, forbidden changes, integrated review
findings, productive overlap and recovery failures per run. A proposed 20%
paired median time improvement and no increase in tokens per accepted task are
targets, not current claims. Missing complete accounting blocks corresponding
performance claims. Eight attempts provide limited evidence, even if all pass.

Release-critical failures include unrelated mutation, lost requirements,
acceptance from stale evidence, silent model substitution, and unsuccessful
fresh-session recovery. Keep the planned eight and forty counts exact while
reporting actual completion and the specific remaining blockers.
